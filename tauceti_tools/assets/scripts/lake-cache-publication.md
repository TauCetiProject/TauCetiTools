# Native Lake publication

The producer's final build writes the native map with `lake build --iofail --rehash -o .lake/outputs.jsonl` when artifact caching is enabled. This is one build, with no subsequent whole-graph output scan. Native `lake cache stage` copies the full map and artifacts after the required checks. Lake already preserves restored archives for publication.

Until the pinned stock Lake includes faster process spawning or bulk restoration, `bulk-unpack-cache.py` prepares a fresh private staging cache in one native `leantar` invocation inside the offline sandbox. It validates the supported layout before atomically installing the expanded tree, removes only the satisfied private mappings, and retains each original archive beside its module. The final Lake build still verifies current inputs and reuses those archives in its native output map; changed sources rebuild normally. Unsupported layouts, existing builds and extraction failures use ordinary Lake restoration. This temporary extraction workaround adds no publication index or reconnect pass; remove it once the stock toolchain supplies the upstream fix.

After candidate processes exit, `lake_cache_publish.py stage` accepts only a complete flat map and ordinary archive files, copying them into a fresh host-owned directory. The isolated publisher repeats this small data boundary before receiving the upload key. Neither copy invokes candidate code or performs network requests. There is no additional publication manifest, omission protocol, inherited-object probe or digest database.

The publisher uploads only the artifacts the bucket lacks. Re-uploading all of them (about 45,000 R2 PutObject operations, Class A) on every publication was nearly all of the bucket's cost, although consecutive publications differ in under a thousand artifacts. The key-free `lake_cache_publish.py check` records the MD5 of each frozen archive and writes a curl configuration of signed HEAD requests (Class B, a twelfth of the price) against the upload endpoint, not the CDN. An inline key-bearing step sends them. The key-free `select` skips an archive only when the bucket answered 200 with an ETag equal to that MD5, so the object in the bucket has exactly the publisher's bytes. A missing, corrupt or differing object, an error, a timeout, or no answer at all uploads the archive, so a failed check costs only the uploads it would have saved. The upload step then PUTs the selected archives with curl, to the URLs and content types `lake cache put-staged` uses, and PUTs the full map only after every archive upload succeeded. A failed upload is retryable from the complete staged artifact; no producer rerun or full-publication switch is required. The finalizer still requires the exact map to be publicly readable before landing.

Run `python3 scripts/test_lake_cache_publish.py --integration` with stock Lean/Lake, curl and openssl. It runs the publisher workflow's own steps against a local TLS fixture with dummy credentials only, and checks failed upload ordering, retry, fresh restoration with stock `lake cache get`, skipping of identical objects, re-upload of missing or differing objects and of everything when the existence check fails, changed-source rebuilding and corrupt-download rejection.
